TEST-85 — Deletion cause and the 6-year records policy

Every deletion has a cause. People with no contact for 6 years are deleted once a year, on 31 December, after their organisation's owners are warned. On staging this runs in test mode: every deletion can be undone, and nothing is written to the legacy database.

Part 1: User request label (done) Part 2: 6-year policy (built, test mode) Live deletion: locked

1. The two deletion causes

CauseWhen it is setCan it be unarchived?
User request DoneAn Organisation owner or IW admin deletes a user with the deletion form and a reason of up to 200 characters.An archived person can be unarchived by IW until their policy deletion date. A deleted person cannot.
Information and Records Management policy NewSet automatically by the yearly cleanup, 6 years after the person's last contact.Never. Unarchive is refused with a message that names the policy and the date.

2. Decisions behind this build

QuestionDecision
6 years from what?From the person's last contact: the latest certificate, IOSH or NEBOSH upload, course finish, course start, registration, login or activity, or the account itself if nothing else exists.
Daily or yearly?Yearly. The cleanup runs on 31 December. A person is due on 31 December of (year of last contact + 6). That keeps data at least 6 full years and up to almost 7.
Which data?People data only: name, email, phone, custom fields, and IOSH or NEBOSH certificate files. Organisations, orders, invoices, licences and products are not touched.
WarningOwners are warned on 1 October (about 90 days ahead) and reminded on 1 December. IW admins get a summary.
First live run31 December 2026, with 6 years, only after IW reviews a dry run and approves live mode.
DashboardsThe User status toggle stays in Reports. Performance dashboards are a separate ticket.

4. How "last contact" is worked out

For each person, across all their organisations, the system takes the most recent of these dates. Archived rows count too, so archiving never brings the date forward.

IOSH / NEBOSH certificate upload
Certificate issue or pass date
Last login or activity
Course finished
Course started / registration
Account created (fallback)

The bars show how recent each date usually is. Whichever is latest wins. The results are stored on the person as users.last_contact_at and users.records_policy_due_on, and refreshed every night at 02:00.

5. What the yearly cleanup does

Step 4 is the same anonymisation as a manual deletion: name becomes "Anonymized Learner", email becomes erased-…@anonymized.invalid, phone and password are cleared, custom fields are removed, organisation memberships end, and the record goes to the Deleted tab. Registrations and own certificates stay as history, under the anonymised name.

6. Safety: test mode now, live mode later

Test mode — on staging now
  • Every deletion can be undone with one command.
  • An encrypted copy of the person is kept until it is reverted.
  • IOSH / NEBOSH PDFs are not deleted from storage, only hidden.
  • Writes to legacy, legacy_lms, legacy_lrs and legacy_admin are blocked. Reads still work.
  • Owner emails are off unless RECORDS_POLICY_NOTIFY_OWNERS=true. Only IW admins get the summary.
  • Nothing runs unless RECORDS_POLICY_ENABLED=true.
Live mode — locked
  • Setting RECORDS_POLICY_MODE=live makes the run stop with "live mode is not approved yet".
  • The approval switch is in config/records_policy.php (live_approved => false). It is not an environment variable, so a server setting can't turn it on.
  • When IW approves, a follow-up change will delete PDFs from S3, keep no copy of the person, and turn on owner emails.

Where the data lives

All the rows this cleanup changes (users, user_emails, attribute_values, tenant_users, employment_periods, certificate_uploads) are in the main Postgres database. The code checked does not write to legacy. The guard is a second safety net in case something does.

8. How to test on staging (no waiting)

You don't have to wait for 02:00 or 31 December. Every step has a button on Admin → Users → More → Records policy (/admin/users/records-policy). Only IW admins who can delete users see it.

One-time setup (developer)

  1. Deploy, then run the migrations: 
    php artisan migrate
  2. Put these in the API .env on staging (api/.env, not the client), then clear the config cache: 
    RECORDS_POLICY_ENABLED=true
RECORDS_POLICY_MODE=test
RECORDS_POLICY_RETENTION_YEARS=6
RECORDS_POLICY_NOTIFY_OWNERS=false

php artisan config:clear

Tester steps

  1. Open Admin → Users, open More, choose Records policy. Status shows On and Test mode: can be restored.
  2. Click Refresh dates now. A message says how many people were updated. Go back to the Archived tab: the Policy deletion date column is filled.
  3. Leave the date as 31 December this year (or pick a later year to include more people) and click Preview who is due. Nothing is deleted. The table shows each person's last contact and policy deletion date.
  4. On one test person, click Delete this person and confirm. (Run cleanup now deletes up to 50 people due on that date.)
  5. Check the app: the person is on the Deleted tab with the cause Information and Records Management policy. Unarchiving them is refused, and their IOSH certificate is on the certificates Deleted tab.
  6. Back on Records policy, under 3. Restore, click Restore on that person (or Restore this run).
  7. Check the person is back exactly as before: name, emails, organisation, custom fields and IOSH certificate.

Same steps from the command line (developer)

php artisan compliance:records-policy-refresh-dates
php artisan compliance:records-policy-run --date=2026-12-31 --dry-run
php artisan compliance:records-policy-run --date=2026-12-31 --user=123
php artisan compliance:records-policy-revert --list
php artisan compliance:records-policy-revert --run=<run id>
php artisan compliance:records-policy-notify --date=2026-10-01 --dry-run

To keep someone out of the cleanup, set users.records_policy_hold = true. A person can be restored once. After a restore they are still due, so the next run deletes them again.

11. Not in this change

  • Live mode: permanent S3 file deletion, no kept copy, owner emails on. This is done after IW approves.
  • The existing IOSH Delete button removes only a local file, but the PDFs are stored on S3. That is fixed together with live mode.
  • Organisation data retention (orders, invoices) needs a separate rule and ticket.
  • A User status toggle on the performance dashboards needs a separate ticket.
  • In reports, archived people's names show as "Anonymised" (TEST-84). Owners can export them only by ID and dates, not by name.
